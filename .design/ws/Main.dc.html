One socket, one run

The job dials the app, not the other way round. It reconnects on a timer rather than only at startup, because a run that begins while the app is down has to attach by itself when the app comes back — the normal case here, not a recovery path.

DEAD LETTER
Both halves of the handshake carry a resume point neither side consumes. next_seq is exactly what would let a reattaching app know what it missed, and observed is exactly what would let the job know it is being watched. Either wire them up or drop the payloads — a handshake that carries unread fields invites someone to trust them.

SHARP EDGE
The inbound pong at channels.py:205 is asyncio.create_task(…) with no reference kept — the only unreferenced task in the harness. Python may collect it before it runs, so the app's liveness check can silently go unanswered. Every other create_task here holds its handle.
04  LOSS & TEARDOWN nothing here may raise into the run
Connection lost
_session() raises → _maintain() swallows it, logs at INFO with _diagnosis(exc), sets _ws = None, sleeps reconnect_s and dials again. Forever, until close().
close()
Send BYE (best effort) → ws.close() → cancel the maintain task. Sets _stopped first so the loop does not redial.
SHARP EDGE
is_connected is self._ws is not None — optimistic. Only a failed send discovers a dead socket, so between the ingress dropping the connection and the next send, the relay believes WS is up and never falls through to HTTP push. With reconnect_s = 30 fixed and no jitter, every job whose app went down also redials in lockstep.
CONFIRMED BUG
At teardown the harness closes this socket before the relay has drained, so a fast run delivers none of its live stream — terminal status included. Measured, and laid out on the Teardown board.
